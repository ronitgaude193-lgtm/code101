# AI Coding Mentor: Full Implementation Context

You are working on **AI Coding Mentor**, a full-stack educational platform at `D:\DBCE`. It teaches students to think like programmers. Instead of handing out answers, it combines a code playground, safe code execution, a step-by-step visual debugger, AI mentoring, "code autopsies" that diagnose misconceptions, adaptive skill tracking and gamification. Everything below describes the code as it exists now. Read the "Known gaps" section before claiming a feature is complete.

---

## 1. Tech stack and how it runs

- **Backend:** Python 3.14, FastAPI 0.162, Uvicorn, Pydantic v2, httpx, PyJWT, psycopg 3 (with `psycopg_pool`) and python-dotenv. Code lives in `backend/app/`.
- **Database:** Supabase PostgreSQL only. SQLite was removed; a leftover `backend/mentor.db` file is unused.
- **Frontend:** React 19 + TypeScript 7 + Vite 8, using `@monaco-editor/react`, `lucide-react` and `canvas-confetti`. Code lives in `frontend/src/`. The production build in `frontend/dist/` is served by FastAPI.
- **Code execution:** Judge0 CE at `https://ce.judge0.com` (free public server, no key). A local isolated sandbox is the fallback when Judge0 is not configured.
- **AI:** Ollama, running locally (`gemma3:latest` at `http://localhost:11434`), is the default provider. Gemini, OpenAI and Groq are also supported. An offline rule-based engine is the fallback.
- **Run everything:** `.\.venv\Scripts\python.exe run_app.py` from `D:\DBCE`. It checks that `DATABASE_URL` is set, runs `init_database()`, prints the Ollama model and starts Uvicorn at `127.0.0.1:8000` with no auto-reload, so restart after backend changes.
  - UI: `http://127.0.0.1:8000`
  - API docs: `http://127.0.0.1:8000/docs`
- **Dev mode:** with `PYTHONPATH=D:\DBCE\backend`, run `uvicorn app.main:app --reload` for the backend and `npm run dev` in `frontend/`.

### Database schema (PostgreSQL, TEXT primary keys generated by the app, JSON stored as TEXT)

1. `users`: id, email (unique), password_hash, full_name, role (default `student`), created_at, updated_at.
2. `student_profiles`: user_id (primary key, foreign key to users), current_level, total_xp, streak_days, last_active_date (an ISO date string), preferred_language, bio.
3. `coding_challenges`: id, title, slug (unique), topic, difficulty, description, initial_code, solution_code, test_cases (JSON `[{input, expected_output, hidden}]`), constraints, hints (JSON list), xp_reward.
4. `code_submissions`: id, user_id, challenge_id (set to NULL if the challenge is deleted), code, language, status, execution_time, memory_used, error_type.
5. `execution_results`: one per submission (unique submission_id), with stdout, stderr, compile_output, exit_code, status_description.
6. `ai_feedback`: id, submission_id, user_id, mode (`learning`, `debugging`, `hint` or `autopsy`), summary, detailed_explanation, and JSON fields hints_given, misconceptions, suggested_topics.
7. `learning_assessments`: per-topic score, strengths, weaknesses and recommendation. **Defined but never written or read.**
8. `student_skills`: unique per (user_id, skill_name), with mastery_level (0 to 100), problems_solved, problems_attempted, error_count, last_practiced.
9. `learning_history`: event_type, details (JSON), xp_earned.
10. `achievements`: code (unique), title, description, badge_icon (a Lucide icon name), xp_reward, milestone_threshold.
11. `student_achievements`: unique per (user_id, achievement_id), with unlocked_at.

All foreign keys to users use `ON DELETE CASCADE`.

## 4. Feature modules in detail

### Code execution
- **Judge0 client:** maps languages to Judge0 IDs (python 71, javascript 63, cpp 54, java 62). Calls `POST /submissions?base64_encoded=false&wait=true` with a 5-second CPU limit and 128 MB of memory. A run counts as successful when Judge0's status id is 3. Exit codes come from the status, because Judge0 omits them by default. A key is sent as RapidAPI headers for `*.rapidapi.com` hosts and as `X-Auth-Token` for any other host. Network errors come back as the status "Network Timeout / Provider Offline", **with no fallback to the sandbox**.
- **Isolated sandbox:** used only when `JUDGE0_API_URL` is empty. Before running, it scans the code's syntax tree and blocks:
  - the imports `os`, `subprocess`, `socket`, `http`, `urllib`, `requests`, `shutil`, `ctypes`, `winreg` and `msvcrt`
  - the calls `__import__`, `eval`, `exec`, `compile` and `open`

  The code then runs in a separate Python process with a 4-second timeout. A blocked import produces "Security Policy Violation".
- **Challenge evaluation:** for each test case, it adds a small runner after the student's code. The runner finds the last function the student defined, calls it with the test input (a tuple input is spread into several arguments), and prints the result (JSON for non-strings). A test passes when the exit code is 0, stderr is empty and the output equals the expected value after stripping quotes. The overall status is Accepted, Wrong Answer or Runtime Error.

### Visual debugger (Python only)
- `tracer_worker.py` runs in its own process with a 3.5-second timeout and a 150-step cap. The code must pass the sandbox's safety check first.
- It uses `sys.settrace` to record, for each line, the line number, event, local variables (shortened values: strings cut at 100 characters, collections at 20 items) and the output so far.
- The frontend (`VisualDebugger.tsx`) shows a timeline with play, pause and step controls and a variable inspector.

### AI mentor and code autopsy
- **Provider order:** if a provider is configured, the LLM is called first (Ollama `/api/chat` with a 45-second timeout, Gemini `generateContent`, or an OpenAI/Groq-style chat API with a 20-second timeout). The model is told to teach rather than give away code and to reply in JSON; the JSON is pulled out of the reply and parsed. **Any error or bad reply falls back silently to the offline rule engine.**
- **Mentor modes:** `learning` (explains concepts), `debugging` (guides toward the bug) and `hint` (gradual hints). The response contains summary, explanation, hints, conceptual_takeaway and related_topics.
- **Offline rule engine:** pattern checks that detect:
  - syntax and indentation errors
  - a loop variable overwriting an accumulator (`total = x` inside a for loop)
  - index-versus-value confusion (`range(len(...))` with `total = i`)
  - an early `return` inside a loop

  Anything else gets general guidance for the chosen mode.
- **Autopsy:** returns primary_failure_reason, syntax_vs_logic, misconception_identified, detailed_walkthrough, a loop timeline showing what each iteration did and where it went wrong, guiding_hint and practice_prompt. The built-in diagnoses are "Index vs Value Confusion", "Premature Loop Termination via Inner Return" and "State Evolution Mismatch".

### Adaptive learning engine (`record_submission_event`, runs on every submit)
- **XP:** the challenge's `xp_reward` on Accepted, otherwise 10 XP for the attempt. Level is `total_xp // 100 + 1`.
- **Streak:** +1 if the student was last active yesterday, reset to 1 after a gap, unchanged if already active today.
- **Skill mastery:** each skill is named after the challenge's topic. Mastery is `clamp(5, 100, 15 + solve_ratio×70 + min(solved×2, 15) − min(errors×1.5, 20))`. A brand-new skill starts at 35 if solved, otherwise 15.
- **Achievements awarded automatically:** First Code Executed (any submit), Bug Hunter (first Accepted), 3-Day Streak (streak of 3 or more) and Master of Loops (5 or more solved in a "Loop" topic). A row is also written to `learning_history`.
- **Dashboard:**
  - the profile, attempts, solves and solve rate
  - skills labelled Strong (70 or above), Developing (40 to 69) or Needs Focus (below 40)
  - weaknesses: mastery below 50, or more errors than solves
  - the last 5 history events
  - DNA scores
  - 3 recommended challenges (currently just the first 3 in the table)
- **Programming DNA:** six scores.
  - logical thinking: from the solve ratio and number of skills
  - debugging: 50 + 4 per solve
  - correctness: the solve ratio
  - speed: always 70
  - hint independence: 95 − 5 per hint request
  - consistency: 50 + 10 per streak day

  It also lists strengths and growth areas and assigns an archetype: Algorithmic Architect, Methodical Debugger, Autonomous Pioneer or Emerging Synthesizer.

### Frontend (`frontend/src/`)
- `App.tsx` switches between tabs held in component state (no router): Playground, Challenges, Dashboard and Achievements. The default challenge is `ch_sum_list`.
- `api/client.ts` is a typed fetch wrapper. `API_BASE` is **hardcoded** to `http://localhost:8000/api`, and the JWT is added automatically. `context/AuthContext.tsx` keeps the session and saves it across page reloads. `types/index.ts` holds the TypeScript models.
- **Components:**
  - `Navbar` shows the level, XP and streak badge.
  - `MonacoPlayground` has the Monaco editor, a language picker (only Python is enabled; JavaScript, C++ and Java show as "Planned"), a stdin drawer and the console.
  - `ChallengeSidebar` shows the description, constraints, visible test cases and hints.
  - `AICodingMentor` has three mode tabs.
  - `AICodeAutopsy` shows the autopsy, loop timeline and misconception.
  - `VisualDebugger`, `DNAProfileView` and `AuthModal` (register and sign-in).
- **Pages:**
  - `PlaygroundPage`: the three-panel coding workspace, with confetti on a successful solve.
  - `ChallengesPage`: browse challenges and use the generator.
  - `DashboardPage`: skill bars, weakness heatmap, activity and DNA.
  - `AchievementsPage`: the badge grid.

## 5. Known gaps and inconsistencies (verified in code)

1. **Two achievements are never awarded.** `ach_autopsy` (FORENSIC_CODER) and `ach_visual_trace` (X_RAY_VISION) exist in the seed data, but nothing in the autopsy or trace endpoints unlocks them.
2. **`learning_assessments` is unused.** The table exists, but no code reads or writes it.
3. **Submission metrics are placeholders.** `execution_time` is saved as a fixed `0.1`, `memory_used` is never filled, and the DNA speed score is always 70.
4. **The "AI" challenge generator uses fixed templates.** It has 3 hardcoded templates and never calls the LLM, so the difficulty setting only labels the result.
5. **Recommendations aren't personalized.** Recommended challenges are the first 3 rows, and each weakness's `recommended_challenge_id` is always empty.
6. **Judge0 gaps:**
   - Student code is sent to a third-party server, and the local import blocking doesn't apply.
   - There is no fallback if the public server is down.
   - Test 3 expects the local sandbox's blocking message, so it will fail while Judge0 is configured.
7. **Only Python works end to end.** Judge0 language IDs exist for JavaScript, C++ and Java, but they are disabled in the editor, the evaluation runner is Python-only and the tracer is Python-only.
8. **LLM failures are invisible.** Errors are swallowed without logging, so a down Ollama server quietly switches to rule-based answers. `/api/health` reports "ollama" whether or not Ollama is reachable.
9. **Configuration issues:**
   - The frontend API URL is hardcoded.
   - CORS allows every origin even though a `CORS_ORIGINS` setting exists.
   - The `APP_SECRET_KEY` default is committed in the code.
   - The `SUPABASE_*` keys are unused.
10. **Migration leftovers:** `backend/mentor.db` is left over from the SQLite version, and parts of the README still describe old status tables.
11. **Achievement titles can be repeated.** `_award_achievement` adds the title to the "unlocked" list even when the insert hits a conflict. Callers check before awarding, so in practice this is a race condition only.

## 6. Conventions to follow when changing the code

- Use the database only through `with get_db() as conn:` and `%s` placeholders. Rows behave like dicts (`row["col"]`). Use `ON CONFLICT ... DO NOTHING/UPDATE`, never SQLite syntax.
- Schema changes go in `backend/app/database/schema.sql` and must stay safe to re-run (`IF NOT EXISTS`, `ON CONFLICT`). It runs on every startup.
- Keep JSON columns as TEXT written with `json.dumps` and read with `json.loads`.
- Never return `solution_code` to clients. Never run student code inside the FastAPI process.
- Add new response shapes to `schemas/all_schemas.py` and mirror them in `frontend/src/types/index.ts`.
- Restart `run_app.py` after backend changes, because it doesn't reload. Rebuild the frontend with `npm run build` so FastAPI serves the new `dist/`.
